# Boson protocol facts

The one home for what we know about Boson's APIs. Everything else in the repo cites a fact by
its id (`F1`…) and never restates it.

- `VERIFIED-DOCS (date)`: re-read in Boson's docs or site on that date. The docs can be wrong.
- `VERIFIED-RUN (date)`: observed on the wire by `scripts/smoke.py` or a live test on that date.
  Only a live run sets this tag. The evidence column quotes the observed event.
- Anything not in this file is UNVERIFIED. Never fill a gap from the OpenAI Realtime API.

Doc URLs below drop the common prefix `https://docs.boson.ai/`.

## Facts

| id | fact | source | status | evidence |
|---|---|---|---|---|
| F1 | The server sends nothing until the client sends `session.update`; `session.created` then acknowledges that first update. `conversation.created` is never emitted. The model must be named either in `?model=higgs-realtime` on the URL or as `session.model` in the first `session.update`, otherwise that update fails. Endpoint: `wss://api.boson.ai/v1/realtime`. | https://docs.boson.ai/models/higgs-realtime/migrate-an-existing-integration · https://docs.boson.ai/models/higgs-realtime/guides/connections-and-sessions | VERIFIED-RUN (2026-10-24) | `scripts/smoke.py`, `results/smoke-20261024T145225Z.jsonl`: no event in 3 s after connect; the first event after `session.update` was `session.created` with `"model": "higgs-realtime"`. |
| F2 | **The docs and the wire disagree.** Docs: `response.done` carries `usage: null` and `status_details: null` on every response, and `status` is only `completed` or `cancelled`. Observed: `status_details` was `null`, but `usage` was populated (`total_tokens`, `input_tokens`, `output_tokens`, `input_token_details.cached_tokens`) on a text-mode response. Audio mode, observed in the live gate run `20261024T160618Z-6e8bdda7`: `usage` populated (296 input, 272 cached, 20 output for one turn). Whether `input_tokens` includes `cached_tokens` is not stated; 272 ≤ 296 is consistent with "included" but does not prove it. | https://docs.boson.ai/models/higgs-realtime/migrate-an-existing-integration · https://docs.boson.ai/api-reference/realtime/server-events | VERIFIED-DOCS (2026-10-24) · contradicted by VERIFIED-RUN (2026-10-24) for `usage` | `results/smoke-20261024T145225Z.jsonl`, `response.done` (text mode): `"status": "completed", "status_details": null, "usage": {"total_tokens": 25, "input_tokens": 22, "output_tokens": 3, "input_token_details": {"cached_tokens": 0}}` |
| F3 | `conversation.item.create` accepts text only. `input_audio` and `input_image` contents are skipped, `system`-role messages are rejected. User messages use `input_text`, assistant messages use `text` (`output_text` is not recognised). `function_call` and `function_call_output` items work. | https://docs.boson.ai/models/higgs-realtime/migrate-an-existing-integration | VERIFIED-DOCS (2026-10-24) | Migrate page, "Events" section. |
| F4 | Audio input goes only through `input_audio_buffer.append`, at most 1 MiB of base64 per event (about 15 s of 24 kHz PCM). Internal processing is 24 kHz, 16-bit, mono PCM. `audio/pcm` accepts 8000/16000/24000/48000 Hz (default 24000); `audio/pcmu` and `audio/opus` also exist. | https://docs.boson.ai/models/higgs-realtime/migrate-an-existing-integration · https://docs.boson.ai/models/higgs-realtime/guides/audio-and-voices · https://docs.boson.ai/models/higgs-realtime/guides/connections-and-sessions | VERIFIED-DOCS (2026-10-24) | Connections page: "max ~1 MiB base64 per append, ≈15 s of 24 kHz PCM". |
| F5 | `conversation.item.done`, `rate_limits.updated` and `input_audio_buffer.timeout_triggered` are never emitted. Extra event types exist (`response.output_audio_transcript.length`, `conversation.context.summarized`, `session.idle_timeout`, `session.max_duration_reached`). Clients must tolerate unknown event types. | https://docs.boson.ai/models/higgs-realtime/migrate-an-existing-integration | VERIFIED-RUN (2026-10-24) for `conversation.item.done` | `results/smoke-20261024T145225Z.jsonl`: 12 events through `response.done` plus 3 s of tail, no `conversation.item.done` (two `conversation.item.added` were sent). The other two never-emitted events are VERIFIED-DOCS only. |
| F6 | `output_modalities` is exactly `["audio"]` (default) or `["text"]`. Mixed or empty lists are rejected. Text mode streams `response.output_text.*`. | https://docs.boson.ai/models/higgs-realtime/guides/connections-and-sessions | VERIFIED-DOCS (2026-10-24) | Session configuration table, `output_modalities` row. |
| F7 | Voices: `"default"`, a Boson preset, or `voice_<id>` registered with `POST /v1/audio/voices` (reference audio ≤ 10 MB, ≥ 3.0 s, plus its transcript). Any non-default voice is validated at `session.update`; an unknown voice or an OpenAI voice name fails the update. | https://docs.boson.ai/models/higgs-realtime/guides/audio-and-voices · https://docs.boson.ai/api-reference/audio/create-a-voice | VERIFIED-DOCS (2026-10-24) | Audio page: "an unknown or inaccessible voice fails the update". |
| F8 | `server_vad` threshold defaults to 0.85 (`prefix_padding_ms` 300, `silence_duration_ms` 500, `min_speech_duration` 0.125 s). `create_response`, `interrupt_response` and `eagerness` are accepted but inert; barge-in always interrupts. `idle_timeout_ms` is rejected. After 5 minutes with no detected user speech the server sends `session.idle_timeout` and closes. | https://docs.boson.ai/models/higgs-realtime/guides/turn-detection-and-interruptions · https://docs.boson.ai/models/higgs-realtime/migrate-an-existing-integration | VERIFIED-DOCS (2026-10-24) | Migrate page, "Session limits": "after 5 minutes without detected user speech". |
| F9 | Transport is WebSocket only. No WebRTC (in progress), no SIP, no `/v1/realtime/calls`, no `output_audio_buffer.*`, no DTMF events. | https://docs.boson.ai/models/higgs-realtime/migrate-an-existing-integration | VERIFIED-DOCS (2026-10-24) | Migrate page, "Connection and lifecycle", first bullet. |
| F10 | Tools: `function` tools plus a server-side `web_search` (`{"type": "web_search"}`). A search appears as a `function_call` item named `web_search` with `"executor": "server"`; the client sends no `function_call_output` and no `response.create` for it. Client tools carry `"executor": "client"`. No MCP tools, no tool approvals. | https://docs.boson.ai/models/higgs-realtime/guides/tool-calling · https://docs.boson.ai/models/higgs-realtime/migrate-an-existing-integration | VERIFIED-DOCS (2026-10-24) | Tool-calling page, "web search" wire section. |
| F11 | Avatar realtime sessions run only in a LiveKit Cloud room (self-hosted is refused with `422 invalid_livekit_url`), are created with `POST /v1/avatar/sessions`, and accept audio only from `transport.publisher_identity` over a LiveKit data stream (24 kHz 16-bit PCM). The LiveKit Agents avatar plugin must be installed from a pinned git commit; the PyPI 1.8.8 release does not work with this API. A first-party LiveKit integration for Realtime is "coming soon". Capacity is limited: `429 capacity_exhausted` with `Retry-After`. | https://docs.boson.ai/models/higgs-avatar/realtime-sessions · https://docs.boson.ai/models/higgs-realtime/integrations/livekit | VERIFIED-DOCS (2026-10-24) | Avatar page: the pin is `warlockee/agents@808a4249850945f91609a9145e50ffea1c9802c4`, a personal fork. |
| F12 | Prices, see the table below. Realtime is billed by tokens; the per-minute audio rates are Boson's estimates for common usage. | https://www.boson.ai/pricing · https://docs.boson.ai/pricing | VERIFIED-DOCS (2026-10-24) | Pricing page: "Actual cost is calculated from tokens consumed." |
| F13 | If billing entitlement is refused mid-session, the server sends an `error` event with `type: "insufficient_quota"` and closes the WebSocket with code `4429`. An invalid or expired ephemeral key closes with code `3000`. | https://docs.boson.ai/models/higgs-realtime/migrate-an-existing-integration · https://docs.boson.ai/models/higgs-realtime/guides/connections-and-sessions | VERIFIED-DOCS (2026-10-24) | Migrate page, "Session limits", quota bullet. |

| F14 | The first `session.update` is acknowledged with `session.created`, every later one with `session.updated` (so a client must not wait for `session.updated` after the first update). An invalid configuration produces an `error` and the session is closed. | https://docs.boson.ai/api-reference/realtime/client-events | VERIFIED-RUN (2026-10-24) for the first ack | `results/smoke-20261024T145225Z.jsonl`: the first `session.update` got `session.created` and no `session.updated`. Doc conflict, unverified: the tool-calling page says an invalid `web_search` config returns `error` and "the session keeps its previous configuration". |
| F15 | Server VAD events: `input_audio_buffer.speech_started` (`item_id`, `audio_start_ms` incl. `prefix_padding_ms`; while the assistant speaks it is the barge-in signal), `input_audio_buffer.speech_stopped` (`item_id`, `audio_end_ms`; a response follows automatically). The clock origin of the `_ms` fields is not stated beyond "position in the input audio stream". | https://docs.boson.ai/api-reference/realtime/server-events | VERIFIED-DOCS (2026-10-24) | Server events, "Input audio" section. |
| F16 | Manual turns: with `turn_detection: null`, appended audio accumulates until `input_audio_buffer.commit`. Commit emits `input_audio_buffer.committed` (`item_id`, `previous_item_id`), transcribes, adds the user item (`conversation.item.added`), and does not start a response; send `response.create`. Both commit and `response.create` are rejected with `error` type `voice_output_task_ongoing` while a response is active. | https://docs.boson.ai/api-reference/realtime/client-events · https://docs.boson.ai/api-reference/realtime/server-events | VERIFIED-DOCS (2026-10-24) | Client events, `input_audio_buffer.commit`: "Committing does not generate a response". |
| F17 | Response events: `response.output_audio.delta` carries `response_id`, `item_id`, `output_index`, `content_index`, `delta` (base64 audio in `audio.output.format`). `response.done` is emitted exactly once per `response_id` with `status` `completed` or `cancelled` (interrupted or `response.cancel`); the reason is not available (F2). `response.created` echoes `metadata` from `response.create` (`null` for VAD-triggered responses). | https://docs.boson.ai/api-reference/realtime/server-events | VERIFIED-DOCS (2026-10-24) | Server events, "Response lifecycle" and "Response object". |
| F18 | Assistant transcript in audio mode: `response.output_audio_transcript.delta` (`delta` text), `.length` (Boson extension, adds `length_ms` of the matching audio), `.done` ("the spoken transcript for a content part is complete"). | https://docs.boson.ai/api-reference/realtime/server-events | VERIFIED-RUN (2026-10-24) | Live audio-mode probe 12:15 Toronto: `response.output_audio_transcript.delta` ("Hello, trainee!") arrived 0.35 s before `response.done`, followed by `.length` and `.done` with the same text. |
| F19 | Input transcription only when `audio.input.transcription.model` is `higgs-stt-3.1`; delivered only as `conversation.item.input_audio_transcription.completed` (`item_id`, `content_index`, `transcript`); billed as transcription (F12). Unset means no events and no charge. | https://docs.boson.ai/models/higgs-realtime/guides/connections-and-sessions · https://docs.boson.ai/models/higgs-realtime/migrate-an-existing-integration | VERIFIED-DOCS (2026-10-24) | Connections page, "Input transcription model". |
| F20 | Session fields: `instructions` is the system prompt; `max_output_tokens` is an integer (clamped to 4096) or `"inf"` (default); `temperature` defaults to 0.3; `tool_choice` is `auto` / `none` / `required` / a named function. | https://docs.boson.ai/models/higgs-realtime/guides/connections-and-sessions · https://docs.boson.ai/api-reference/realtime/client-events | VERIFIED-DOCS (2026-10-24) | Client events: "`max_output_tokens` integers are clamped to `4096`". |
| F21 | Realtime connections have a concurrency limit; exceeding it closes the WebSocket with code `1013` (retry later). The limit's value is not documented. | https://docs.boson.ai/account-billing/usage-and-limits | VERIFIED-DOCS (2026-10-24) | Usage and limits, "Concurrency". |
| F22 | Higgs TTS 3: `POST /v1/audio/speech`; `input` up to 5,000 characters (50,000 with `stream: true`), longer returns 400 `input_too_long`; `voice` is a preset name or `voice_<id>` (mutually exclusive with `ref_audio`); `response_format` `mp3` (default) / `opus` / `pcm` / `wav` / `aac` / `flac`; `stream: true` requires `pcm` and yields raw 16-bit / 24 kHz / mono PCM. Presets listed: `chloe`, `eleanor`, `jake`, `marcus`, `nora`, `oliver`. | https://docs.boson.ai/api-reference/audio/create-a-speech · https://docs.boson.ai/models/higgs-tts/overview · https://docs.boson.ai/models/higgs-tts/voices | VERIFIED-DOCS (2026-10-24) | TTS overview: streaming body is "a raw 16-bit / 24kHz / mono PCM byte stream". Host: the create-a-speech OpenAPI declares `servers: https://api.boson.ai`. |
| F23 | Server-side auth: `Authorization: Bearer <API_KEY>` header on the WebSocket handshake to `wss://api.boson.ai/v1/realtime`. (Browsers use an ephemeral key in the subprotocol instead.) | https://docs.boson.ai/models/higgs-realtime/guides/connections-and-sessions | VERIFIED-RUN (2026-10-24) | `scripts/smoke.py` sent this header and the session opened (`results/smoke-20261024T145225Z.jsonl`, `session.created`). |
| F24 | Turn detection is set at `session.audio.input.turn_detection`: `{"type": "server_vad"}`, `{"type": "semantic_vad"}`, or `null` for manual commit (F16). With `null`, appended audio does not start a response on its own. | https://docs.boson.ai/models/higgs-realtime/guides/connections-and-sessions · https://docs.boson.ai/models/higgs-realtime/guides/turn-detection-and-interruptions | VERIFIED-RUN (2026-10-24) | IHBench AC-14 live replay (`ihbench-higgs/results/ac14-20261024T153754Z.jsonl`, 3 audio commits): no `response.*` event before the client's `response.create`. |
| F25 | Replay acks and ordering: a text item sent with `conversation.item.create` is acked by `conversation.item.added`. An audio commit is acked first by `input_audio_buffer.committed` (`item_id`, `previous_item_id`) and later by `conversation.item.added` for the same id (role `user`, content `input_audio`). Items interleaved as text, commit, text, commit keep that order: each `previous_item_id` is the item sent just before. | https://docs.boson.ai/api-reference/realtime/server-events | VERIFIED-RUN (2026-10-24) | Same AC-14 log: chain `d941cc6a` (assistant text) → `15a8c726` (user audio, prev `d941cc6a`) → `71ca752a` → `1154e236` (prev `71ca752a`) → `599ce5b8` → `216d22ef` (prev `599ce5b8`). |
| F26 | **TTS docs and wire disagree on `model`.** Docs: `model` is optional, default `higgs-tts-3` (F22). Observed: `POST /v1/audio/speech` without `model` returns `400 invalid_request_error` (pydantic `missing`, loc `model`); with `"model": "higgs-tts-3"`, `voice: "chloe"`, `response_format: "pcm"`, `stream: true` it returns `200`, `content-type: audio/pcm`. The endpoint also returned `429` `rate_limit_error` / `rate_limit_exceeded` with no `Retry-After` header; the limit's value and window are undocumented. | https://docs.boson.ai/api-reference/audio/create-a-speech | VERIFIED-RUN (2026-10-24) | Probes from the main session, 12:04 Toronto: 400 body names `loc ('model',)`; 200 run returned 36,480 bytes for "Hi."; the live gate run `20261024T160329Z-aafb9522` hit the 429 on its first TTS call. |
| F27 | The assistant transcript is not a record of what was heard. In audio mode the whole response text can arrive in the first `response.output_audio_transcript.delta`, well before the audio finishes; after a barge-in stops the audio, the transcript already holds the full sentence. A judge reading the transcript cannot tell whether an answer was cut off. | https://docs.boson.ai/api-reference/realtime/server-events | VERIFIED-RUN (2026-10-24) | Probe 12:15 Toronto: full sentence in the first delta at 0.279 s, audio done at 0.631 s. Gate run `20261024T163013Z-00df50f2`: barge-in stop time 252 ms on st-5 turn 1, yet the judge's transcript holds that answer complete. |

## UNVERIFIED — test before relying

- Whether every `voice_<id>` created through the TTS voices API (F7) works as a Realtime
  `audio.output.voice`, for every voice. The docs say yes; nobody here has seen it.
- Latency when the input is text (`input_text` item plus `response.create`) rather than audio.
- Whether the model emits parallel tool calls in one response, and how `response.done` lists
  them.
- How long `session.max_duration_reached` allows (the docs give no number).
- Whether `response.output_audio_transcript.done` is sent for a cancelled response (F27 settles
  that the transcript is not cut).
- The clock origin of `audio_start_ms` / `audio_end_ms` (F15).
- The value of the Realtime concurrency limit (F21).
- TTS 3 sample rates for non-streaming formats, and whether `voice: "default"` is accepted on
  `/v1/audio/speech` (F22 lists only the six presets).
- Whether the 5-minute idle close (F8) also applies with `turn_detection: null`.
- Whether server VAD (F8, `silence_duration_ms` 500) splits one scripted user turn with an internal
  pause ("Sorry, wait. What comes first…") into two user turns and two responses. Seen indirectly in
  gate run `20261024T161045Z-d663176a`: st-5's judge got "No problem." and the real answer reached
  st-6. Confirm on the wire by logging `speech_started` / `response.created` per turn.
- Whether `input_tokens` already includes `input_token_details.cached_tokens` (F2). Audio-mode
  usage is reported; the inclusion rule is still unstated.
